# 订阅源复盘

覆盖 M4a–M4c（订阅源引擎、服务与 API、界面）。

## 1. 范围

交付了订阅源的完整链路：`SourceSpec` 的 RSS 归一化、`engine/rss.py` 与
`engine/feed.py` 两个引擎、两张新表、`RssService`、11 个 API 端点、四个界面。

## 4. 做对的

**先量再写。** 动手前对全量 1,344 个归档跑了一遍统计，拿到的不是「大概一成能用」
而是精确的四档分布。这直接决定了「两条腿」这个方案 —— 只有 10.6% 的话，光靠归档
源产品太薄。

**第二条腿的成本评估是对的。** 两条腿共用模型、表、API、界面，分派只是服务层里
一个 `if`。增量成本就是 `engine/feed.py` 一个文件（约 200 行），换来可用性从
10.6% 到「想订什么都行」。

**所有「不支持」都显式报错。** `singleUrl` 型源抛异常而不是返空、feed 解析失败抛
带原因的异常而不是返回空列表。因为「不支持」和「今天没更新」在界面上长得一模
一样，而两者的下一步动作完全不同。

**OpenAPI 与 schema 从代码生成，不手写。** 两份 spec 是从运行中的 FastAPI 应用
导出的，两份 SQL 是从 SQLAlchemy 模型生成的。手写的契约文档会漂移，生成的不会。

## 5. 问题与根因

### 问题一：两条计划里的假设是错的

动手前的计划写翻页字段是 `ruleNextArticles`，实测是 `ruleNextPage`（449 个 /
33.4%）；计划还假设「无 `ruleArticles` 就回退标准 feed 解析」能救回一批源，实测
URL 像 feed 的只有 4 个（0.3%）。

**根因**：那两条都来自对我们自家 `manage/publish/rss.py` 产出格式的印象，而归档
里绝大多数源来自上游。**自家产出的样本不能代表语料。**

### 问题二：`_collect_flat_rules` 的优先级不确定

好几个旧字段名指向同一个规范名，而原实现迭代源数据 —— 谁在 JSON 里靠前谁赢。同一
个源在不同序列化下会解析出不同结果。

**根因**：原实现只处理书源，而书源那边的重名字段（`ruleContentUrl` 与
`ruleContentUrlNext`）极少同时出现，所以这个不确定性一直没暴露。加 RSS 时
`ruleNextPage`/`ruleNextArticles` 会同时出现，问题才浮出来。

### 问题三：`singleUrl` 型源一开始会进候选池

`registry.scan()` 的 `enabled` 判定原本是 `is_complete and not needs_js`。
`singleUrl` 型源规则可能齐、也可能不含 JS，于是 292 个跑不了的源会进池。

**根因**：`enabled` 的语义是「这个源我们跑得了」，而原判定只覆盖了书源的两种失败
方式。新增一种失败方式（需要浏览器）时，判定没跟着扩。

## 8. 后续结论

订阅源可用了，而且「两条腿」这个结构让它不受归档质量制约 —— 用户自填 feed 这条
路永远是 100% 可用的。

三件事留给后续：

1. **quickjs** 能把归档源的可用率从 10.6% 推到 ~38%（427 个需要 JS 的源里大部分
   会活过来）。这是单项投入回报最高的一件。
2. **UA 配置**：有站点按 UA 拒绝。一个可配的默认 UA 成本很低。
3. **未读数**：现在只有已读数，因为服务端不缓存列表。要真未读数就得缓存全量列表，
   那又回到「订阅文章不缓存」的取舍 —— 需要产品决策，不是技术问题。
