### PC 不是「顺带能用」

手机浏览器是主场景，但 PC 必须同样好用 —— 这是原生 APP 不需要考虑的约束。桌面上
翻章靠点屏幕左右 25% 是不可接受的（2560px 宽屏上那是 640px 的死区），所以键盘是
桌面的主交互：

| 键 | 作用 | 页面 |
| --- | --- | --- |
| `←` `→` | 上一章 / 下一章 | 正文 |
| `t` / `s` / `h` | 目录 / 设置 / 换源 | 正文 |
| `p` / `a` | 朗读开关 / 自动翻页开关 | 正文 |
| `Esc` | 逐层关闭：抽屉 → 工具栏 → 回详情页 | 正文 |
| `/` | 聚焦搜索框 / 跳搜索页 | 搜索、书架 |
| `g` / `r` | 网格↔列表 / 检查更新 | 书架 |

两条硬规则：**输入框里不拦截**（否则搜索框的方向键没法移光标），**带修饰键的组合
不拦截**（`Ctrl+←`、`Cmd+[` 是浏览器和系统的）。侧栏底部把快捷键列出来，不让人猜。

| # | 功能 | 级 | 实现 |

有的按「月榜/完结」），不可能跨源合并成统一的分类树。这就是第一层必须是选源的原因。

和搜索的分工：搜索是「我知道要什么」，发现是「给我看看有什么」。后端完全不同
（搜索跨源 fan-out，浏览是单源），但返回形状一致，所以详情页那条链不变。

### 全书进度滑块不是装饰

上千章的书里跳转，拖滑块比翻目录快得多 —— 这是原版那一屏最实用的一项。滑块用
1-based，和用户看到的「第 N 章」一致，省掉一次心算。

### 朗读与亮度都带着 Web 的硬限制

- **朗读用浏览器的 `speechSynthesis`，不是服务端 TTS。** 音色取决于用户装了什么
  语音包，所以音色列表是运行时枚举的（还要监听 `voiceschanged` —— Chrome 首次
  查询常返回空）。按段落切成多条 utterance，不是整章一条，否则暂停后回不到原处。
  必须由用户手势触发，这是浏览器的自动播放策略。
- **亮度只能压暗。** Web 没有屏幕亮度 API，实现是在正文上盖一层黑色遮罩调透明度。
  所以滑块的 100% 是「不压暗」而不是「最亮」。这个限制在界面上写明了，否则用户会
  以为坏了。遮罩必须 `pointer-events: none`，不然整个正文页点不动。

### 读到一半换源要能接着读

「读着读着这个站点看不了了」是这个产品最常见的故障场景（源语料大面积失效）。
所以换源不是把人甩回详情页：

- 换源时把当前章节名送给后端，后端取新源的目录**按章节名重新定位**进度，
  然后前端留在正文页直接加载那一章；
- 不同源的章节切分不同（有的多个楔子、有的把一章拆两页），所以不能直接沿用
  序号 —— 实测「乙源多一个楔子」这种情况下沿用序号会退一章，而用户看不出来；
- 定位方式如实告知：精确命中就直接读，按位置估的会提示「可能有偏差，请确认」，
  目录取不到就回详情页手动选。

**不做自动换源。** 换源会改变你在读哪个源（内容可能有删改、错字），这是需要
知情的决定；而且失败率本来就高，自动换源会让「源」这个状态在用户无感的情况下
持续漂移。

### 为什么 B2 不是可选项

聚合搜索要并发打十几个源，单源超时 `(6, 12)` 秒，而归档里大量源已经死了。没有
中间态和源统计时，这三种完全不同的情况在界面上长得一模一样：

1. 这本书确实没有；
2. 十个源里九个需要 JS，当前版本跑不了；
3. 源站这次都没答上来，过会儿再试就有。

三者的下一步动作分别是「换关键词」「别指望了」「重试」。所以搜索响应里带着
`sources_tried` / `sources_ok` / `js_skipped` / `failed`，界面按它们分三种空态文案。

## 书架与离线

| # | 功能 | 级 | 实现 |
| --- | --- | --- | --- |
| S1 | 书架列表（封面网格 / 列表两种视图） | L1 | `GET /shelf` |
| S2 | 加入 / 移出书架 | L1 | `POST /shelf`、`DELETE /shelf/{book_key}` |
| S3 | 显示「读到第 N 章」+ 点击续读 | L1 | 有进度直接进正文，没有则进详情 |
| S4 | 批量下载章节到服务端缓存 | L1 | `POST /shelf/{key}/download`，单批上限 200 章 |
| S5 | 下载进度查询 + 已缓存章节列表 | L1 | `GET /shelf/{key}/cached` 带 `downloading` |
| S6 | 清空某书缓存 / 清空全部 | L1 | 详情页单本，「我的」页全部 |
| S7 | 书架排序（最近阅读 / 加入时间 / 书名） | L2 | 前端排序，不加接口 |
| S8 | 多选批量操作（批量移出 / 批量移动到分组） | L2 | 显式的「多选」按钮进入选择态 —— Web 上长按不可靠，原版那套长按菜单搬不过来 |
| S9 | 书架分组（建组 / 移动 / 改名 / 解散） | L1 | `GET/POST /shelf/groups*`，分组名就是标识 |
| S10 | 批量检查更新 + 未读数角标 | L1 | `POST /shelf/check-updates`，202 + 轮询进度 |
| S11 | 本地书籍导入（txt / epub） | L3 | 见下「竞品有而我们没有的」 |

离线的语义是「**服务端**缓存了正文」而不是「浏览器缓存了页面」。飞行模式下仍需
能连到服务端 —— 这是家里局域网的常见情形（断外网不断内网）。

### 分组没有「分组表」

分组名直接存在 `reader_shelf.group` 上，空串 = 未分组。没有独立的分组实体，于是
「建组」就是把书移进一个新名字、「解散」就是把组里的书移成空串、「改名」就是一次
批量 UPDATE —— 都不需要额外的生命周期管理，也不会出现「空分组」这种只能靠界面
打扫的残留。代价是改名要扫一遍该组的书，但书架是几十到几百本的量级。

### 未读数不存

`unread` 由 `chapter_count`（上次检查数到的章节数）减去进度算出来。存一份就要在每
次翻页时跟着改对，而它随时可以算。`chapter_count = 0` 的含义是「还没查过」而不是
「没有章节」—— 界面据此不显示角标，而不是显示 0。

### 检查更新是后台任务，不是一个请求

一本书要两次抓取（详情 + 目录），几十本就是几分钟，撑不过任何合理的请求超时。所以
`POST /shelf/check-updates` 返回 202 + `task_id`，前端按 1.5 秒轮询。默认每本之间
隔 1 秒 —— 书架里的书往往来自同一个站点，不限速就是对人家连着打几十个请求。

同一个账号同时只能跑一轮：第二次请求返回 409 带着正在跑的那个 `task_id`，让界面
直接接上去轮询，而不是另起一轮重复抓取。

### 两套凭据是故意的

管理端那个口令能触发 `POST /sources` —— 服务端会去拉用户给的任意 URL（SSRF）。
读者登录看书不该顺带拿到这个能力，管理端的共享口令也不该冒充某个具体读者。
所以两个 cookie、两组守卫，两个方向都有测试压着。

## 第一次打开会看到什么

一个全新安装、还没有任何账号时：

1. `/web` 放行，身份是隐式的本机身份（`user_id = 0`）—— 新克隆与 CI 不配账号
   也要能直接用。
2. 第一次注册会把这段「无账号时期」攒下的书架和进度**认领**过去。
3. 一旦有了账号，隐式身份立刻失效，之后必须登录 —— 否则第一个人的书架会对
   局域网里任何人敞开。

## 竞品有而我们没有的

2026-10-10 和 gedoor/legado（APP 本体）、hectorqin/reader、tthking/reader-dev 逐项
对过一遍，逐项对照表在
[`development/platform-foundation/013-reference-implementations.md`](../../development/platform-foundation/013-reference-implementations.md)。
下面是缺口，按价值排序 —— 全是 L3，意思是「这一版明确不做」，不是「不需要」。

| # | 功能 | 谁有 | 为什么现在不做 |
| --- | --- | --- | --- |
| X1 | JS 规则求值 | 全部 | 不是产品决策，是最大的技术债。书源可解析率 ~63%、订阅源 10.6% 的天花板全在这里 —— **不解决这条，上面所有功能清单都没有意义，用户搜不到书** |
| X2 | 本地书籍导入 / OPDS / WebDAV | 三家都有 | 自托管阅读服务的基本盘，不是锦上添花：用户手里已有的 txt/epub 现在完全没地方放。**这不是 Web 形态的限制** —— 两个服务端竞品都做了（上传到服务端），我们只是没做 |
| X3 | 真离线（断网可读） | 只有 APP 本体 | 见 `N6`。现有理由只覆盖「断外网不断内网」，覆盖不了地铁 —— 这条取舍该重新过 |
| X4 | 书签 / 划词高亮 / 替换净化 | APP 本体 | 长尾阅读功能，单项价值低但加起来是「像个正经阅读器」。`content_select_action.xml` 的八项是现成清单 |
| X5 | 精确搜索 / 按分组限定搜索范围 | APP 本体 | 候选池只有几百个源，全打一遍的成本还能接受 |
| X6 | 换源按响应时间排序 / 按字数筛 | APP 本体 | 我们按「实跑成功过的排最前」排，信号不同但方向一致 |
| X7 | 目录加载字数 / 重新分段 / 去重复标题 | APP 本体 | 都要多一轮抓取或额外的正文后处理 |
| X8 | 阅读时长统计 | APP 本体 | 要一张新表 + 前端埋点，而它不影响「能不能读到书」 |
| X9 | 书源调试器（逐条规则的流式日志） | APP 本体、reader-dev | 我们有候选池的实跑统计与最近错误，粒度更粗但够定位「这个源还活着吗」 |
| X10 | `singleUrl` / WebView 型源 | 全部 | 占订阅源归档 21.7%。服务端要支持就得接无头浏览器，见 `R12` |

### 反过来，我们有而它们没有的三件

1. **采集源管线 + 候选源池。** 竞品清一色「用户自己去粘贴远程书源 URL」；我们是
   登记上游 → 自动采集 → 实跑统计 → 按真跑通过的排序。源质量是这个产品的命门。
2. **搜索失败可解释**（`B2`）。竞品统一是「没找到」，我们分三种空态三种文案。
3. **订阅可以自填标准 feed**（`R2`）。这条路 100% 可用，不受 legado 归档质量制约
   （归档只有 10.6% 能跑）。三个竞品都只做 legado RSS 源。
