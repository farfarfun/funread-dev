# 范围与约束

这一章记录**为什么**范围是这样的。每条都对应一个实测数字或一个结构性事实，不是
偏好。

## 只在局域网用

session cookie 是 `secure=False`。这不是疏忽：服务通常通过 `http://192.168.x.x:8811`
访问，而 `secure` cookie 在纯 http 下**根本不会被浏览器送回来** —— 加上它等于
让登录直接失效。

代价是这套鉴权不能暴露到公网：中间人可以直接抓走 session，而账号化之后抓走的是
具名账号而不只是一个只读口令。要上公网还缺三样：HTTPS、`secure=True` 的 cookie、
登录速率限制。三者一起留给后续，见
[`project-governance/004-roadmap.md`](../../project/project-governance/004-roadmap.md)。

## JS 规则不求值

Legado 的规则语言里可以嵌 JS（`@js:` / `<js>` / `java.*` 宿主桥）。当前版本遇到
这类规则**显式报错**，不静默降级。

| 源类型 | 纯 Python 可跑 | 接上 quickjs 后（预估） |
| --- | --- | --- |
| 书源 | ~63% | ~95% |
| 订阅源 | 10.6%（1,344 个里 142 个） | ~38% |

接 quickjs 要实现一整套宿主 API（`java.ajax`、`java.getCookie`、`cache` 等），
是独立一轮的工作量，不和界面开发挤在一起。

**为什么必须显式报错**：静默返空会让界面上「这个源不支持」和「这个源今天没更新」
长得一模一样。前者该换源，后者该等 —— 分不清就只能瞎点。

## 不做 WebView 型订阅源

`singleUrl` 非空的订阅源占归档 21.7%（292 个）。它们的工作方式是把一个页面塞进
WebView 让用户直接看，没有可解析的列表结构。做它意味着引一个无头浏览器，那是另
一个数量级的部署复杂度。

这类源不在订阅源目录里列出来 —— 列出来也点不开。订阅时也当场拒绝，而不是订上
之后每次点开都给一个错误提示。

## 不缓存订阅文章正文

订阅文章时效性强、量大（一个活跃订阅一周几千篇），缓存正文的收益很低而占用很高。
所以 `reader_rss_article_state` 只存已读/收藏状态，正文每次重抓。

代价：没有网就读不到订阅文章。这是和小说的明确差别 —— 小说有「下载到服务端缓存」，
订阅没有。

## 没有「未读数」

服务端不缓存文章列表，所以它**不知道**一个订阅总共有多少篇文章。能给的只有
「已读了多少篇」（`read_count`）。界面上的未读由前端按「当前这一页」算。

想要真正的未读数就得缓存全量列表，那又回到上一条的取舍。

## 正文缓存全局共享，不按人隔离

`reader_chapter_cache` 故意不带 `user_id`：它是正文缓存而不是个人数据 —— 就是
公网上那一页，没有隐私含义。按人隔离只会让同一章正文存 N 份。

两个后果写在这里以免将来被当成 bug：

- 下架一本书时，只有在**没有别人也把它放在架上**时才清缓存；
- 清空某本书的缓存会影响所有读这本书的人。可以接受，因为代价只是一次重新抓取，
  而一个卡住的坏缓存比这糟得多。

## 搜索分页是近似的

`GET /reader/search` 的 `offset` 切的是**这一次调用**的结果集。每次调用都重跑
一轮实时 fan-out，所以第二页不保证严格接着第一页 —— 上一次超时的源这次可能答了。

排序在源响应相同时是确定的（命中源多的在前），所以它对「加载更多」够用、对深
分页不对。前端按 `book_key` 去重，避免列表里冒出重复条目。

## 范围外的完整清单

- JS 规则求值；
- `singleUrl` / WebView 型订阅源；
- 浏览器端 Service Worker 离线；
- 订阅文章正文缓存；
- 公网暴露（HTTPS、`secure` cookie、速率限制、口令重置、邮箱验证）；
- Alembic 迁移（建表走 `create_all` + 手写迁移，与现状一致）。
