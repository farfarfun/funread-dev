# 为什么是两条腿

## 那个 10.6%

对 `funread-dat/hubs/rss/source` 全量 1,344 个归档实测（`load_source` + 静态扫描）：

| 档 | 数量 | 占比 |
| --- | --- | --- |
| 规则不全 | 529 | 39.4% |
| 规则完整但需要 JS | 427 | 31.8% |
| `singleUrl`（WebView 型） | 292 | 21.7% |
| **规则完整 + 纯 Python 可跑** | **142** | **10.6%** |

142 个。作为一个「订阅源目录」，这个数字是能用的下限 —— 但只有这一条腿的话，
产品上太薄：用户打开订阅页，看到一百多个大多是漫画站的源，很可能一个都不想订。

## 第二条腿：用户自填 feed

用户贴 `https://xxx/feed.xml`，走 lxml 解析 RSS 2.0 / Atom / RDF。

这条路径 **100% 可用** —— 标准 feed 就是结构化 XML，没有规则、没有 JS、没有
WebView。用户想订什么就订什么，完全不受上面那张表制约。

## 为什么不只做第二条腿

归档里那 1,344 个源是这个项目已有的资产。142 个能直接用的源意味着「打开就有东西
可看」，而不是「先去别处找 feed 地址回来贴」。对一个自托管的阅读应用，首次使用
的空白期是最容易放弃的时刻。

## 两条腿的成本几乎只有一个类

两者共用：同一个 `RssArticle` 模型、同一张订阅表、同一张文章状态表、同一组 API、
同一套界面。差别只在「怎么拿到一页文章」：

- `kind="legado"` → `RssSourceEngine`（规则求值）
- `kind="feed"` → `parse_feed`（XML 解析，约 200 行，不引 feedparser）

分派在 `RssService` 内部一个 `if`。所以第二条腿的增量成本就是 `engine/feed.py`
一个文件，换来可用性从 10.6% 到「想订什么都行」。

## 推翻的两条旧假设

动手前的计划里有两条假设，实测都是错的，记在这里以免重复：

**1. 翻页字段不是 `ruleNextArticles`。** 归档里真正在用的是 `ruleNextPage`
（449 个 / 33.4%）；`ruleNextArticles` 是我们自家 `manage/publish/rss.py` 产出的源
在用。两个都要认，归一到同一个键。

**2.「无 `ruleArticles` 就回退标准 feed 解析」救不回任何源。** 实测 1,344 个源里
URL 看着像 feed 的只有 4 个（0.3%）。那 529 个「规则不全」的源基本都是 WebView 型
网页，不是 feed。所以第二条腿必须靠用户自己提供地址，不能从归档里挖。
