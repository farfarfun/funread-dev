# 对标 Folo：差距与分期

这一章回答一个反复被问到的问题：「接入类似 Folo 的功能，实现到哪了？」

结论先写在前面：**订阅阅读器的骨架已经齐了**（M4a/M4b/M4c，随 1.1.127 发布），
Folo 真正的差异化部分**一行都没有**。但其中相当一部分，在局域网自托管这个定位下
抄过来没有意义 —— 下面逐条说清哪些要做、哪些明确不做、理由各是什么。

## 先对齐定位差，否则功能对照会误导

| | Folo | funread |
| --- | --- | --- |
| 形态 | 多用户云服务 | 局域网自托管，单人或家庭 |
| 账号 | 平台账号，跨设备同步 | 本机账号，邀请码开户，不上公网 |
| 内容来源 | 平台托管的源目录 + RSSHub | Legado 归档（142 个可跑）+ 用户自填 feed |
| 商业模式 | $POWER 代币、订阅付费、创作者打赏 | 无，自己给自己用 |

**这张表是下面所有取舍的依据。** Folo 的社交与代币是它的商业模式，不是阅读功能；
一个单人自托管的阅读器照抄「关注他人的订阅列表」，没有可关注的人。

## 差距清单

| 能力 | Folo | funread 现状 | 处置 |
| --- | --- | --- | --- |
| 文章订阅与阅读 | 有 | **已有**，11 个端点 / 4 个页面 / 87 个测试 | — |
| 自填任意 feed | 有 | **已有**，且三个 Legado 竞品都没有 | — |
| 已读、收藏、分类 | 有 | **已有** | — |
| AI 摘要 / 翻译 / 日报 | 核心卖点 | 无，零 LLM 依赖 | **范围外**，见下 |
| 播客与音频 | 独立 tab | 解析侧已接住（2026-10-18），缺播放器 | **M10** |
| 视频 | 独立 tab | 解析侧已接住，缺播放器；那个小缺陷已修 | **M10** |
| 图片流 | 独立 tab | 只当缩略图 | **M10** |
| 社交媒体内容 | 独立 tab | **其实已经能用** —— 贴 RSSHub 地址即可 | 补 UI 呈现，M10 |
| OPML 导入导出 | 有 | **已有**（2026-10-18，R14/R15） | — |
| 发现 / 源搜索 | 社交化发现页 | `GET /rss/sources` 带 `q` 搜归档 | 补精选清单，M11 |
| 关注他人、分享列表、热门榜 | 有 | 无 | **范围外** |
| 代币打赏 | 有 | 无 | **范围外** |

## 明确不做的

### AI 摘要、翻译、日报

2026-10-18 决定**先不做**，不是「以后再说」式的搁置，而是这一期明确不排。

三个依赖都还没有答案，而它们必须一起定，单独定任何一个都会返工：

- **推理放哪**。云端 API 实现最简、质量最好，但订阅文章正文要发给第三方，且按量
  计费 —— 一个活跃订阅一周几千篇，成本得先算。本地模型（Ollama 一类）正文一步
  不离开局域网，和「不上公网」的定位最一致，代价是要求这台机器跑得动模型，且
  摘要与翻译质量明显不如云端。
- **密钥与开关怎么进配置**。按 M9 的规矩该走 `resolve_setting` 那条链，默认关闭、
  不配就整个功能不出现。
- **摘要落哪张表**。`reader_rss_article_state` 现在只存已读与收藏，正文每次重抓
  （见 [003-feature-list.md](./003-feature-list.md)「订阅文章不缓存正文」）。摘要
  是花钱算出来的，必须缓存，所以它是这个「不缓存」决定的第一个例外。

真要做的时候，第一刀应该是**可插拔的 provider 接口**，让云端与本地是同一抽象下的
两个实现，而不是先绑死一家。

### 社交：关注、分享订阅列表、热门榜

定位差那一节已经给了理由 —— 单人自托管没有社交图谱。

值得单独说的是：Folo 的「发现」里真正有用的那部分**不是社交**，是「帮我找到好
源」。这部分以非社交的形态保留在 M11（精选清单 + OPML），社交的壳不要。

### 代币与打赏

与阅读功能无关。

## 要做的

### M10 多内容类型

Folo 把内容分成文章、社交、图片、视频、音频几个 tab。funread 现在只有文章一种
呈现。四件事的成本差得很远，所以按成本排：

**播客与音频 —— 数据已经在解析路径上，被主动丢掉了。** `feed.py:94` 这一行：

```python
if url and (not kind or kind.startswith("image/")):
    return url
```

`_image_of()` 拿到了 `<enclosure>`，但只接受 `image/*`，于是播客的音频地址被丢在
原地。而 `RssArticle`（`models.py:79`）九个字段里也没有装它的地方 —— 只有
`image: str`。

所以播客支持不是「从零做多模态」，是：`RssArticle` 加一组媒体字段（url / type /
时长）、`_image_of` 旁边加一个 `_media_of`、前端加一个 `<audio>` 播放器。Legado
侧的 `engine/rss.py` 没有 enclosure 概念，这一条只对自填 feed 生效 —— 而播客几乎
都是标准 feed，正好落在那条 100% 可用的腿上。

**视频**：同一组字段，前端换成 `<video>` 或外链嵌入。顺带修掉下面记的那个缺陷。

**图片流**：解析侧不用改（`image` 字段已经有了），改的是列表布局 —— 摄影类 feed
用现在的「缩略图 + 标题」列表看不了，要网格。这是纯前端。

**社交媒体**：**不需要新功能**。RSSHub 把微博、Twitter 一类转成标准 feed，用户现在
贴地址就能订。缺的只是呈现 —— 短内容在「标题 + 摘要」的卡片里会退化成一行标题
加一行重复的正文。做法是让卡片按内容形态切换，而不是新增一条订阅通路。

### M11 发现与迁移

**OPML 导入导出** —— **已交付（2026-10-18）**。做的时候按下面的判断走了「先入库
再验证」那条，验证由已有的 `last_error` 机制在第一次打开时完成，没有引入后台任务。
留着当时的理由：

- 标准格式，所有阅读器都支持，是从 Inoreader / FreshRSS / Folo 迁进来的唯一通路；
- 纯本地，不碰网，没有隐私与成本问题；
- 实现很薄：解析 XML 拿到一组 feed URL，批量调已有的
  `RssService.subscribe_feed()`（`rss_service.py:197`）。导出是反向，更简单。

要先定的只有一件：导入时**逐条验证还是先入库**。现在 `subscribe_feed` 是同步抓一次
再入库、失败不入库（见 [flows/002-subscribe.md](../../design/rss-subscription/flows/002-subscribe.md)）。
一份 OPML 动辄上百条，逐条同步抓会让导入等很久，而且其中必然有已经挂掉的源。倾向
「先全部入库，再后台逐条验证，失败的在列表里标 `last_error`」—— 该字段已经有了。

**精选 feed 清单**：内置一份人工挑的高质量 feed（技术、新闻、博客），不依赖 Legado
归档。归档只有 10.6% 能跑，当「发现」用内容太薄，而自填那条腿是 100% 可用的 ——
精选清单正是把用户直接推上那条腿。

代价要说清：这是一份**需要长期维护**的清单，源会挂、会换地址。所以它该是一个可以
不更新也不出错的静态文件，而不是一个服务。

## 顺带记下的两个现存问题

都是写这一章时核对代码发现的，不属于上面任何一期，但在同一片代码上：

**1. `media:content` 不检查 type，视频地址会被当成图片。** `_image_of()` 的
`for name in ("thumbnail", "content")` 直接返回 `node.get("url")`，没看 `type` 或
`medium`。`media:content` 是 `video/mp4` 时，这个 URL 会进 `RssArticle.image`，
再被 `ArticleCard.vue:30` 塞进 `<img :src>` —— 得到一张坏图。

触发条件窄，所以一直没暴露：`thumbnail` 优先级在前，而多数视频 feed（YouTube 就是）
两个都给。只给 `media:content` 不给 `media:thumbnail` 的才会中招。M10 加 `_media_of`
时一并修。

**2. `probe.py:44` 的提示过期了。** 还印着「该源含 JS 规则，当前阶段跑不通
（phase 2 接 quickjs）」，而 quickjs 2026-10-16 就接上了。一行注释，但会让人以为
带 JS 的源不能排查。
