# 进度与离线缓存

## 进度存字符偏移，不存滚动像素

`reader_progress.char_offset` 是正文里的字符偏移。

为什么不存像素：换了字号、行距、设备宽度或字体之后，像素值毫无意义 —— 一个在
手机上记下的 3200px 放到桌面宽屏上可能已经越过章节末尾。字符偏移是内容本身的
属性，换算回大致位置总是成立的。

换算是比例式的，不精确但稳定：

```
恢复：scrollTop = (char_offset / 总字符数) × (scrollHeight - clientHeight)
保存：char_offset = (scrollTop / (scrollHeight - clientHeight)) × 总字符数
```

## 回写节流 3 秒，**并且**离开页面补一次

只节流会丢掉最后一段 —— 用户往往读到一半就直接切走或锁屏，而那一段正是最需要
记住的位置。所以除了节流定时器，还在三处强制 flush：

- `pagehide`（iOS Safari 上比 `beforeunload` 可靠）；
- `visibilitychange` 转 hidden（切后台、锁屏）；
- `onBeforeUnmount`（路由离开）。

切章前也强制 flush 一次，否则这一章读到哪就丢了。

进度写失败**不打断阅读**：下一个节流窗口会再试。一次写库失败换来一个错误弹窗
是明显不划算的交易。

## 离线缓存是服务端缓存

`reader_chapter_cache` 存在服务端。「离线」的语义是**正文已经抓下来了**，而不是
「浏览器缓存了页面」—— 飞行模式下仍需能连到服务端。

这在家里局域网是常见情形（断外网不断内网），也是为什么不做 Service Worker：
真正的瓶颈是源站抓取而不是我们这一跳。

### 正文请求要带 `book_key`

`POST /reader/content` 带了 `book_key` 后端才会读写缓存。不带就是每次实时抓。
前端在正文页永远带着。

### 空正文不写缓存

`save_cached_chapter` 对空内容直接返回。把一次失败的抓取缓存下来等于**永久坏掉
这一章** —— 之后每次都命中缓存，再也不会重试。

## 批量下载

`POST /shelf/{key}/download` 返回 202 加一个 `task_id`，真正的抓取在
`BackgroundTasks` 里串行跑，章节之间停 0.3-0.5 秒。

- **串行 + 停顿，不并发**：这是后台任务，没人在等它，而把一个小站打挂的代价是
  整个源以后都用不了。
- **单批上限 200 章**：串行加停顿的话，一本三千章的书会占住一个 worker 一个小时。
  客户端按切片走目录。
- **已缓存的跳过**：所以中断后重跑是幂等的，前端的「下载未缓存章节」直接复用。
- **同一本书已有任务在跑时 409**，并把在飞的 `task_id` 带回去。两个串行抓取同一
  本书只是把源站打两遍。

### 任务登记是进程内的

`DownloadTracker` 在内存里，不落库。它回答的是「此刻有没有在抓这本书」，这本来
就是本进程的属性；「有哪些章节」的权威答案在 `reader_chapter_cache` 里，前端单独
读。所以重启丢掉这份登记只损失一个 spinner，不丢数据。

已知限制：多 uvicorn worker 下 A worker 起的下载对 B worker 不可见。服务跑单进程，
而 DB 里的章节列表两边都会收敛，所以接受。

后台函数包了 `try/except` 把异常记进 tracker —— 任务在响应之后才跑，未捕获的异常
只会进服务端日志，前端会永远转圈。

## 下架时的缓存处理

缓存全局共享（不带 `user_id`），所以 `remove_shelf_book` 先查还有没有别人把这本
书放在架上，**没有才清缓存**。无条件清掉会顺手废掉另一个人已经下载好的章节。
