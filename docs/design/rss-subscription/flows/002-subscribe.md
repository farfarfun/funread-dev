# 订阅流程

## 腿一：从目录订阅归档源

```
订阅源目录
   │  GET /rss/sources（本地查表 + 读源文件，不打网）
   ▼ 点「订阅」
   │  POST /rss/subscriptions {kind:"legado", url_id}
   │  服务端先解析源：
   │    ├─ singleUrl 型 ──→ 422「该订阅源需要浏览器环境」（但目录本来就不列它）
   │    ├─ 规则不全 ─────→ 400 列出缺哪些字段
   │    └─ 不在候选池 ───→ 404
   ▼ 成功（201）
直接跳进这个订阅的文章列表
```

订阅成功后**直接进文章列表**而不是回目录。用户刚订了一个源，下一步一定是看看
里面有什么。

## 腿二：自填 feed 地址

```
点 [+] → 模态
   │  POST /rss/subscriptions {kind:"feed", feed_url}
   │  服务端同步抓一次并解析：
   │    ├─ 非 http/https ────→ 400「feed 地址必须以 http:// 或 https:// 开头」
   │    ├─ 抓不到 ──────────→ 400 带 HTTP 状态
   │    ├─ 是 HTML 页面 ────→ 400「这是一个 HTML 页面而不是 feed 地址」
   │    ├─ 没有 item/entry ─→ 400「这个地址里没有 item/entry，可能不是 feed」
   │    └─ 超过 8MB ────────→ 400 拒绝解析
   ▼ 成功（201，响应带 preview = 条目数）
   │  toast：「已订阅「Hacker News」，当前 30 篇」
关闭模态，刷新订阅列表
```

**失败不入库。** 并且每种失败都有自己的文案 —— 这是用户唯一能据此改正的东西。
一句「订阅失败」会让人无从下手（是地址打错了？网站挂了？还是这个地址不是 feed？）。

`preview` 那个数字是故意的：它让用户当场确认「订对了」，而不是订完还要点进去
看一眼。

## 阅读文章

```
文章列表
   │  GET /rss/articles?sub_id=...
   │  ├─ has_content=false ──→ 点文章直接 window.open 外跳，并标已读
   │  └─ has_content=true
   ▼ 点文章
   │  GET /rss/article?sub_id=...&link=...
   │  ├─ 失败 ──→「读不到这篇文章」+ [重试] [在浏览器里打开] [回列表]
   │  └─ 成功 ──→ 正文（消毒后）+ 自动标已读
```

**正文失败也要给「在浏览器里打开」。** 我们解析不了的页面，浏览器几乎总能显示 ——
把用户堵在一个错误页上毫无必要。

## 已读与收藏的乐观更新

标已读/收藏都是**先改本地再发请求**，失败再回滚。这两个状态无足轻重，等一次往返
才变灰会让列表感觉很顿。

收藏时把标题、链接、时间、配图一起传给后端存一份快照 —— 收藏必须能在文章滚出
源站首页之后照常渲染。
