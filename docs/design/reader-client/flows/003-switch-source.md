# 换源

## 为什么要有换源

一本书在不同站点上都有，而站点会死。换源是这个产品应对源失效的主要手段，所以它
出现在三个地方：详情页顶栏、正文工具栏、以及任何「读不到」的错误态里。

## 流程

```
点「换源」（详情页顶栏 / 正文工具栏 / 任何「读不到」的错误态）
   │  GET /reader/sources?book_key=...
   │  （按书名重新搜一次 —— 书架只记了「当前在读的源」）
   ▼
来源列表（底部抽屉，当前源标注「当前」）
   │
   ▼ 选一个
   │  先把当前进度落盘 —— 后端要靠它（章节名 + 序号）在新源的目录里定位
   │  POST /shelf/{book_key}/source
   │  ├─ 改写书架行的 url_id / book_url，清掉 toc_url
   │  ├─ 清掉这本书的章节缓存
   │  └─ 取新源的目录，把进度重新定位过去，返回定位方式
   ▼
   ├─ method = exact / normalized ──→ **留在正文页**，直接加载定位到的那一章
   ├─ method = position ───────────→ 同上，但提示「可能有偏差，请确认」
   └─ method = none（目录取不到）──→ 回详情页让用户手动选章
```

### 从正文页换源要留在正文页

这是「读到一半源挂了」这个场景的全部意义。把人甩回详情页等于让他在上千章的
目录里重新找自己读到哪 —— 那比不换源还烦。

只有一种情况回详情页：新源的目录取不到（`method = none`）。这时留在正文页只能
显示一个任意章节，回详情页手动选是唯一诚实的做法。

## 进度重定位：这是数据正确性问题

不重定位的后果不只是「体验差」：书架上仍写着「读到第 500 章」，而那个序号在新源下
指向**别的内容**。用户点「续读」会跳到一个陌生位置，而且**看不出哪里错了** ——
他只会以为自己记错了，或者以为这个源的内容不对。

所以 `POST /shelf/{book_key}/source` 会联网取新源的目录并改写进度记录，
返回落在哪一章以及**怎么定位的**：

| `method` | 含义 | 界面 |
| --- | --- | --- |
| `exact` | 章节名精确命中 | 成功提示，直接接着读 |
| `normalized` | 剥掉编号前缀与标点后命中 | 成功提示，直接接着读 |
| `position` | 名字对不上，按比例估的 | **警告**提示「可能有偏差，请确认」 |
| `none` | 新源目录取不到，进度没动 | 警告 + 回详情页手动选 |
| `skipped` | 本来就没有进度可搬 | 普通提示 |

定位逻辑在 `funread/legado/reader/matching.py`，纯函数、29 个单测。三条规则：

1. **先按章节名精确比**，再按归一化名比（`第100章 惊蛰` / `100.惊蛰` /
   `第一百章 惊蛰` / `惊蛰(上)` 都要能互相对上 —— 不同源的编号与标点习惯差异极大）。
2. **重名时取离「按位置估出来的位置」最近的那个。** 网文里「番外」「第一章」这种
   重复章名很常见，取第一个命中会把读到后半本的人扔回开头。
3. **名字对不上才按比例估。** 比例映射在章节数相同时退化成原下标，所以它是
   「直接沿用下标」的严格推广：数量接近时一样准，数量差很多时（有的源把章节
   合并了，1000 章变 100 章）明显更好。首尾精确对齐。

### 字符偏移不跨源沿用

定位到新章后 `char_offset` 归零。新源这一章的长度和分段都不一样，沿用偏移会把人
扔到一个随机位置 —— 退回章首是唯一诚实的选择。

### 一次抓取失败不等于换源失败

换源本身是本地写库，在重定位之前就已经成功了。所以新源目录取不到时返回 200 加
`method = none`，而不是 502 —— 后者会让人误以为源根本没换，于是再点一次。

## 为什么不做自动换源

当内容抓取失败时，技术上可以自动试下一个源。没做，两个理由：

1. **会悄悄改变你在读哪个源。** 不同源的内容可能有删改、错字、甚至是盗版拼接。
   换源是个需要用户知情的决定。
2. **一次网络抖动就会触发。** 失败率本来就高，自动换源会让「源」这个状态
   持续漂移，而用户完全无感 —— 下次打开发现内容风格变了却不知道为什么。

所以保持手动，但把手动这条路做顺：三个入口都能换、换完留在原地接着读、定位方式
如实告知。

## 为什么换源要清缓存、要重算整条链

**不同源的章节切分方式不同。** 甲源的「第 100 章」和乙源的「第 100 章」很可能不是
同一段内容 —— 有的源把一章拆两页，有的源把楔子算第一章。所以：

- **章节缓存必须清。** 留着就是把甲源的正文配上乙源的章节号，读起来是乱的。
- **目录必须重拉。** 序号和 URL 全变了。
- **进度只能按序号勉强对齐。** 这是已知的近似 —— 换源后进度可能偏几章。比记录
  一个无意义的精确值要好。

缓存是全局共享的，所以清缓存会影响所有读这本书的人。可以接受：代价是一次重新
抓取，而一个章节号错位的缓存比这糟得多。

## 从正文页换源

正文页换源后不是原地刷新，而是 `router.replace` 回**详情页**。因为当前章节序号
在新源下已经不可信，停在正文页只能显示一个任意章节。回详情页让用户重新选一次，
是唯一诚实的做法。
